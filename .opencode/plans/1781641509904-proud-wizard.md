# Plan: Expand `/plan` and `/build` commands — grill-with-docs + TDD by default

## Problem

The current `/plan` command goes straight to writing a plan file without first interviewing the user. Requirements are underspecified and the plan has no TDD-informed structure (no behavioral test specifications, no interface design step).

The current `/build` command reads the plan and implements, but has no TDD workflow (no red-green-refactor loop, no test-first discipline).

## Solution

### `/plan` command — three-phase workflow

1. **Interview phase** — follow the grill-with-docs methodology (one question at a time, challenge vague language, cross-reference CONTEXT.md, update CONTEXT.md inline as terms resolve)
2. **TDD design phase** — guided by the TDD skill's planning checklist: confirm interface changes needed, identify which behaviors to test (prioritize), design for testability, identify deep module opportunities
3. **Plan phase** — write the plan file incorporating both the interview findings and the TDD-informed design

The plan file Acceptance Criteria section becomes a list of **behavioral test specifications** (what the system does through its public interface), not implementation steps.

### `/build` command — TDD execution

Inject TDD skill content so the build agent follows the red-green-refactor loop:
- Vertical slices (one test → one implementation → repeat)
- Each acceptance criterion from the plan becomes a tracer bullet
- No speculative implementation

### Injected files

All injected via `!cat` with project-local fallback to global path:

| File | Purpose |
|---|---|
| `grill-with-docs/SKILL.md` | Interview methodology |
| `grill-with-docs/CONTEXT-FORMAT.md` | Format for CONTEXT.md updates |
| `grill-with-docs/ADR-FORMAT.md` | Format for ADR creation |
| `tdd/SKILL.md` | TDD workflow + anti-patterns |
| `STANDARDS.md` | Coding standards |

You are in planning mode. This session has three phases — do not skip Phase 1 or Phase 2.

## Phase 1 — Interview

Follow the grill-with-docs methodology above. Interview the user relentlessly about this feature, one question at a time using the interactive prompt tool. Walk every branch of the decision tree until you reach a complete shared understanding of:

- Exactly what needs to be built
- All edge cases and constraints
- How it fits with the existing codebase and domain model
- What "done" looks like

If a question can be answered by exploring the codebase, explore it instead of asking.

Update `CONTEXT.md` inline whenever a term is resolved. Offer an ADR only if the decision is hard to reverse, surprising without context, and the result of a real trade-off.

Do not move to Phase 2 until the interview is complete.

## Phase 2 — TDD design

Using the TDD methodology above and what you learned in Phase 1:

- Confirm what interface changes are needed
- Identify which behaviors matter most to test (prioritize; you can't test everything)
- Design the public interface for testability — identify deep module opportunities
- List the behaviors to test as behavioral specifications (what the system does, not how)

Ask the user to confirm the interface design and testing priorities before proceeding.

## Phase 3 — Write the plan

Write the plan to `.opencode/plans/<timestamp>-<slug>.md` (Unix timestamp + kebab-case slug).

The file must contain exactly these three sections:

### Implementation Approach

A clear description of what changes will be made and why, including the public interface design and module structure.

### Acceptance Criteria

A checklist of behavioral test specifications derived from the interview and TDD design phase. Each item describes observable behavior through a public interface — not implementation details.

- [ ] <behavioral specification>

### Verification Commands

All commands needed to confirm correctness (tests, lint, build, type-check, etc.).

Tell the user the path to the plan file when done.

Implement using TDD — vertical slices, one acceptance criterion at a time:

1. Take the first unchecked acceptance criterion from the plan
2. Write a failing test for that behavior (RED)
3. Write the minimal code to make it pass (GREEN)
4. Refactor if needed — never while RED
5. Repeat for the next criterion

After all criteria are implemented, run every command listed under **Verification Commands** in the plan. Do not stop until all criteria pass and all commands succeed.
```

## Problem

`AGENTS.md` currently mixes two concerns:

1. **Agent behaviour rules** — how the agent communicates, uses tools, and manages files
2. **Coding standards** — how code should be written (naming, typing, testing, etc.)

There is no structured workflow that ensures:
- The plan agent incorporates coding standards when writing implementation plans
- The build agent follows acceptance criteria and runs verification commands
- Finished work is reviewed against standards before being considered done

---

## Solution

Three custom slash commands (`/plan`, `/build`, `/review`) that form a lightweight, optional development workflow. No new agent files needed — the commands augment the existing built-in `plan` and `build` agents.

### New file: `STANDARDS.md`

Contains all coding standards extracted from `AGENTS.md`. `AGENTS.md` retains only agent-behaviour rules.

**Sections extracted to `STANDARDS.md`:**
- Function Design
- Domain
- Typing
- Naming
- Documentation
- Imports
- Testing

**Sections remaining in `AGENTS.md`:**
- General
- File System
- Git
- GitHub
- Shell (PowerShell)

`STANDARDS.md` is deployed globally to `~/.config/opencode/STANDARDS.md` by the sync script.

---

### Plan file format

Written by the plan agent to `.opencode/plans/<timestamp>-<slug>.md`:

```markdown
# Plan: <feature name>

## Implementation Approach

<description of what changes will be made and why>

## Acceptance Criteria

- [ ] <testable statement>
- [ ] <testable statement>

## Verification Commands

```bash
<command 1>
<command 2>
```
```

---

### `/plan` command — targets `plan` agent

Instructs the plan agent to:
1. Read `STANDARDS.md` (injected via `!cat` shell output — project root first, global fallback)
2. Write a plan file to `.opencode/plans/<timestamp>-<slug>.md` containing:
   - Implementation approach
   - Acceptance criteria (checklist of testable statements)
   - Verification commands (test, lint, build, etc. — sourced from project config)

---

### `/build` command — targets `build` agent

1. Reads the most recent plan file via `!ls -t .opencode/plans/*.md | head -1 | xargs cat`
2. Instructs the build agent to:
   - Implement the feature as described in the plan
   - After implementing, run every command under **Verification Commands**
   - Confirm each acceptance criterion is met
   - Fix any failing criterion or command before stopping

---

### `/review` command — no fixed agent target (runs in whichever agent is active)

1. Reads the most recent plan file via `!` syntax
2. Reads `STANDARDS.md` via `!cat` (project root first, global fallback)
3. Instructs the agent to:
   - Run all verification commands from the plan file and report results
   - Check each acceptance criterion against the current code
   - Check changed files against `STANDARDS.md`
   - List all violations with file + line references
   - If violations are found: describe each one; user tabs to `build` to fix, then returns to `/review`
   - Loop until all criteria pass and no violations remain
