# Enforce Testing Through Planning, Build, and Review

## Problem

Three gaps mean the workflow does not reliably enforce that behavior is tested:

1. **Planning**: The plan template says criteria should be "observable behavior through a public interface" but does not explicitly say the builder must write a test for each criterion before implementing it. The TDD mandate is implicit.

2. **Build**: The orchestrator BUILD step says "implement using red→green TDD" and "after each criterion passes, mark [x]." The mark-complete trigger is ambiguous — the builder can mark a criterion done by inspecting code, with no test written.

3. **Review**: The correctness reviewer accepts "a specific line of code" as evidence that a criterion is MET. This allows zero-test builds to pass review. No reviewer checks whether tests exist for each planned behavior.

## Implementation Approach

### 0. `/plan` Phase 1 (Grilling) — add explicit testing questions

During the interview phase, the agent must explicitly ask about testing. Add a dedicated testing question block to the Phase 1 interview topics in `plan.md`:

- What level of testing is expected? (unit, integration, end-to-end, or a mix)
- What kind of tests? (pure unit against logic, tests through the public API, snapshot/regression tests, property-based, etc.)
- Which behaviors MUST have tests vs which can be left without? (critical paths only, everything, or something in between)
- Are there behaviors that are intentionally untested and why?

These are grilling questions — ask them one at a time via the interactive prompt tool, not as a list.

**File:** `.opencode/commands/plan.md` — Phase 1 interview topics

### 1. `/plan` Phase 3 (Plan template) — Testing Approach section

Add a mandatory **Testing Approach** section to the plan template (between Implementation Approach and Acceptance Criteria). It records what was decided in Phase 1:
- Testing level and kind
- Which behaviors require tests
- Any explicitly untested areas and the rationale

This section is read by the builder during BUILD and signals the expected test structure.

**File:** `.opencode/commands/plan.md` — Phase 3 plan template

### 2. `/plan` Phase 3 — make the test contract explicit in acceptance criteria

Add one sentence to the Phase 3 plan-writing instructions (in `plan.md`): each acceptance criterion is a behavioral claim that the builder will verify with a failing test before implementing. This surfaces in the plan file itself, which the builder reads.

**File:** `.opencode/commands/plan.md` — Phase 3 "Acceptance Criteria" description

### 2. Orchestrator BUILD — require test before marking criterion done

Tighten the mark-complete rule in step 3 of the BUILD section: a criterion may only be marked `[x]` after both (a) a test exercising that criterion passes and (b) the implementation makes it pass. Explicitly state: checking off a criterion without a passing test is a violation.

**File:** `.opencode/agent/afk-orchestrator.md` — BUILD step 3

### 3. Correctness reviewer — require test evidence per criterion

Update "What to check" step 1 to:
- Remove "a specific line of code" as valid evidence
- Require that each MET criterion cites a test name and file that verifies the behavior
- Explicitly flag any criterion with no identifiable test as UNMET

**File:** `.opencode/agent/afk-reviewer-correctness.md` — step 1

## Acceptance Criteria

- [x] `plan.md` Phase 1 interview topics include explicit testing questions (level, kind, which behaviors must be tested)
- [x] `plan.md` Phase 3 template includes a mandatory `## Testing Approach` section capturing the Phase 1 decisions
