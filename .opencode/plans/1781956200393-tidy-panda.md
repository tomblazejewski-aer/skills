# AFK Loop — Strengthen afk-reviewer-standards to Catch Missed Violations

## Root Cause

The `afk-reviewer-standards` agent misses two categories of clear violations:

1. **Multiple `assert` statements per test** (`test_base.py`): The hint "assert on full objects, not individual properties" is interpreted loosely — the LLM sees `assert result.axis == "primary"` and doesn't flag it because `result` IS an object. It misses that the rule means "assert the whole object at once, not one field at a time."

2. **Large function returning None with multiple concerns** (`renderer.py`): `generate_plot` is 100 lines, returns `None`, and has 7+ distinct steps (collect methods, decide layout, build figure, add traces, set axis labels, set title, write HTML). The reviewer fails to flag this because it reviews the diff line-by-line rather than evaluating the function as a complete unit.

Both violations are clearly covered by STANDARDS.md. The problem is the reviewer's instructions, not the standards document.

Two specific instruction weaknesses:
- **"Focus on the diff, not unchanged code"** — makes the reviewer read additions as isolated lines rather than reading the full function to assess holistic concerns like length, return type, and single concern.
- **Vague hint list** — abstract phrases like "single concern, return values not side effects" give the LLM room to rationalise violations away.

## Implementation Approach

Rewrite step 2 of `afk-reviewer-standards.md` to:

1. **Read the full file** for each changed file (using the Read tool), not just `git diff`. Use `git diff` only to identify which files changed — then read those files completely.

2. **Replace the vague hint list** with concrete, mechanical criteria the LLM cannot rationalise past. Specifically:
   - **Testing**: A test function with more than one `assert` statement is a violation unless all asserts are on a single pre-constructed expected object via one `== expected` comparison. Flag any test that asserts individual properties in separate `assert` calls.
   - **Function design**: Flag any non-trivial function that returns `None` AND has more than ~20 lines of body — this signals mixed logic and side effects. Flag any function longer than ~50 lines as likely violating single concern. List the distinct operations a function performs; if there are more than one, it fails.

3. **Add an explicit strictness directive**: "Apply every rule mechanically. Do not give the benefit of the doubt. If a rule clearly applies, report it as a violation."
