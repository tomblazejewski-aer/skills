# Reduce AFK review cycles: pre-flight scan + grep-first review

## Root cause

Two compounding problems cause repeated review failures in the same files:

1. **Builder doesn't pre-flight touched files.** The builder implements new criteria in files that already contain STANDARDS.md violations. Reviewers read the full file and flag those pre-existing violations. Next cycle the builder fixes them — but touches the file again, causing the reviewer to check it again and find *more* pre-existing violations it hadn't reached yet. This "whack-a-mole" pattern drove Cycles 1–3 in the reference plan.

2. **Standards reviewer reads linearly through large files.** Relying on top-to-bottom reading means the reviewer stops when it has enough findings, missing violations deeper in the file (e.g. inline imports at line 1201–1307 were missed in Cycle 2 but found in Cycle 3 after those lines were touched again).

## Implementation Approach

### 1. `afk-orchestrator.md` — pre-flight sub-step in BUILD

Add a new sub-step between the current steps 1 and 2:
> "For each file you plan to modify, read its full content and check it against STANDARDS.md. Fix any pre-existing violations **before writing new code**. Commit nothing — just fix them. This ensures reviewers see a clean file in the first review rather than discovering layers of pre-existing debt across multiple cycles."

This goes immediately after reading the prior FAIL findings (step 2) and before implementing new criteria (step 3). The builder should treat touched-file cleanup as part of the feature work, not separate.

**File:** `.opencode/agent/afk-orchestrator.md` — BUILD section, between current steps 2 and 3

### 2. `afk-reviewer-standards.md` — grep-first scan

Before reading any file for context, use `rg` to find all instances of known violation patterns across the complete file in one shot. This guarantees comprehensive coverage regardless of file length. After finding the candidate lines, read the surrounding context to confirm each one.

Known patterns to search (these recur most often across repos):
- Inline imports: `rg "^\s+(import |from .* import)" <file>` — imports with leading whitespace are inside a function/class body
- `Optional[...]` type usage: `rg "Optional\[" <file>`
- String-literal type annotations: `rg ': "[A-Z]|-> "[A-Z]' <file>`
- Multiple asserts per test function — grep for `assert` within test functions, then count per function

**File:** `.opencode/agent/afk-reviewer-standards.md` — What to check, step 2
